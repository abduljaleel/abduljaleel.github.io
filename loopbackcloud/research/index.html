How it actually works.

Engineering design notes on the architecture behind Loopback Cloud — the trade-offs, invariants, and control planes that make a local multicloud sandbox behave like production.

NOTE-001

In-process vs Docker-backed engines

Most services run as fast in-process Go handlers inside the emulator binary — low latency, shared state, easy snapshots. Services marked with a dot on the Features page (Lambda, RDS, OpenSearch, EKS, etc.) spin up real Docker containers when fidelity demands it: actual Postgres for RDS, real OpenSearch nodes, containerized Lambda runtimes. The router picks the backend per service; clients see identical API shapes either way.

NOTE-002

MCP tool surface design

The built-in MCP server exposes 85 tools grouped by cloud and concern: inspect (list/describe resources), provision (create/update/delete), labs (chaos, clock, cost, snapshots, interconnect, GenAI). Each tool maps to an internal /_loopback/* or cloud-native API call. Tools return structured JSON so agents can chain operations — create a bucket, attach chaos, fast-forward the clock, read the cost meter — without parsing CLI output.

NOTE-003

Interconnect authorize gate

Cross-cloud traffic is denied at the proxy layer by default. An attachment record links a source cloud endpoint to a destination; until POST /_loopback/interconnects/authorize marks it active, requests crossing cloud boundaries receive a native-shaped 403 AccessDenied. Chaos can sever or slow authorized links independently. This models real interconnect semantics without requiring VPC peering, ExpressRoute, or Cloud Interconnect configuration.

NOTE-004

IAM why-403 diagnostics

When a call is denied, the standard error gives little context. The /_loopback/why-403 endpoint replays the request against the effective policy set — identity policy, resource policy, SCP-style boundaries — and returns the exact statement index, condition key, and failing Effect: Deny or missing Allow. This mirrors how engineers debug production IAM, but runs synchronously against in-memory policy documents.

NOTE-005

Clock and TTL semantics

Each cloud maintains a virtual clock independent of wall time. Fast-forward advances expiry for STS tokens, DynamoDB TTL attributes, SQS visibility timeouts, EventBridge schedules, and Certificate Manager renewals. Freeze pauses all time-dependent logic for deterministic tests. Background sweepers compare resource timestamps against the virtual clock on each tick — no real-time waits required in CI.

NOTE-006

Cost meter wiring & agent-native sandbox philosophy

The Cost Lab hooks into service-level operation counters — S3 PUT/GET, Lambda invocations, DynamoDB RCUs — and applies published pricing tables per cloud. Because the meter reads the same virtual clock as TTL logic, a month of accrual compresses into seconds. The broader design goal: agents should provision, break, and learn against real API shapes with zero blast radius — every control plane (MCP, console, /_loopback/*) is a first-class interface, not an afterthought.
